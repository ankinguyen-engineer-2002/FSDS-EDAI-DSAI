Làm chủ tháp trừu tượng 3 tầng API của Apache Flink: từ kiểm soát từng sự kiện và bộ hẹn giờ ở tầng đáy DataStream API / ProcessFunction, tư duy bảng động Dynamic Table trong Table API, truy vấn khai báo với Flink SQL (TUMBLE, HOP, SESSION), đến phối hợp cả 3 API trong cùng một tác vụ thực chiến.

Ở Chặng 3, chúng ta đã giải quyết bài toán cốt tử của xử lý luồng: dùng nhãn thời gian gốc Event Time kết hợp tín hiệu Watermark để đóng các cửa sổ thời gian (Tumbling, Sliding, Session) một cách chính xác bất chấp độ trễ mạng. Bước sang Chặng 4 (Trạm 4.1 → 4.3), chúng ta đi vào câu hỏi thực thi của kỹ sư dữ liệu: làm thế nào để viết mã điều khiển Apache Flink biến đổi sự kiện giao dịch Order #8888 (productId="PRD-99", amount=450000, event_time="10:00:50") trong luồng SalesEvents? Thay vì ép kỹ sư dùng một công cụ cứng nhắc cho mọi bài toán, Apache Flink cung cấp một tháp giao diện lập trình ứng dụng phân tầng từ cấp thấp mệnh lệnh (Imperative) đến cấp cao khai báo (Declarative), tất cả cùng hội tụ về một bộ lập lịch thực thi vật lý duy nhất.

Trạm 4.1: Tháp Trừu tượng Flink APIs & Giải phẫu Tầng Đáy DataStream API / ProcessFunction

Apache Flink thiết kế hệ sinh thái lập trình theo mô hình tháp 3 tầng trừu tượng (Layered APIs), đặt sự đánh đổi trực diện giữa hai trục: Năng suất phát triển ở đỉnh tháp và quyền kiểm soát chi tiết ở đáy tháp (Slide 41–42; Stream Processing with Apache Flink, Ch. 5 & Ch. 6, tr. 116–121). Càng đi lên đỉnh tháp, mã nguồn càng ngắn gọn và dễ bảo trì; càng lặn xuống đáy tháp, kỹ sư càng nắm toàn quyền thao túng từng bản ghi, từng vùng nhớ trạng thái và từng nhịp đồng hồ:

  • Tầng Đỉnh — Flink SQL (Highest Productivity / Declarative): Ngôn ngữ truy vấn khai báo chuẩn ANSI SQL, dễ viết và dễ đọc nhất đối với cả kỹ sư dữ liệu lẫn chuyên viên phân tích. Người dùng chỉ cần mô tả kết quả mong muốn (What), toàn bộ việc tối ưu hóa kế hoạch thực thi và quản lý trạng thái do bộ tối ưu hóa tự động đảm nhiệm.
  • Tầng Giữa — Table API (Relational Operations in Code): Giao diện lập trình kiểu ngôn ngữ chuyên biệt (Language-Integrated Query DSL) nhúng trực tiếp trong Python, Java hoặc Scala. Table API biểu diễn logic dưới dạng chuỗi các phép toán đại số quan hệ (select, filter, group_by, join) có kiểm tra kiểu dữ liệu ngay lúc viết code và dễ dàng tách hàm tái sử dụng.
  • Tầng Đáy — DataStream API & ProcessFunction (Lowest-Level Control / Imperative): Tầng lập trình mệnh lệnh cung cấp quyền kiểm soát từng sự kiện đơn lẻ (event-by-event control), truy cập trực tiếp vào bộ nhớ trạng thái có khóa (Keyed State như ValueState, ListState, MapState) và đăng ký bộ hẹn giờ (TimerService) theo cả Event Time lẫn Processing Time.
Sự đánh đổi giữa tốc độ phát triển (Declarative SQL) và quyền kiểm soát cấp thấp (Events, State, Timers) cùng luồng toán tử DataStream.

Bản chất của DataStream và 7 phép biến đổi nền tảng (Slide 43)

Ở tầng DataStream API, cấu trúc dữ liệu trung tâm là đối tượng DataStream<T> — được định nghĩa chính xác là một chuỗi sự kiện có kiểu dữ liệu tường minh và có thể vô hạn (a typed, possibly unbounded sequence of events, Slide 43). Khi sự kiện Order #8888 (SalesEvent(productId="PRD-99", amount=450000, event_time="10:00:50")) chảy vào hệ thống, kỹ sư lắp ghép các phép biến đổi (Transformations) để tạo thành đồ thị luồng dữ liệu (Dataflow Graph). Bảng dưới đây phân tích 7 phép biến đổi cốt lõi của DataStream API cùng cơ chế của KeyedProcessFunction:

Phép biến đổi (Operation) Đầu vào → Đầu ra Cơ chế vận hành trên luồng sự kiện Minh họa với sự kiện Order #8888 (PRD-99)
map() DataStream[T] → DataStream[R]
(Tỷ lệ 1 : 1)		 Biến đổi từng sự kiện độc lập sang đúng một sự kiện mới thông qua hàm ánh xạ một-đối-một. Không làm thay đổi số lượng bản ghi trên luồng. Chuyển đổi đơn vị tiền tệ của Order #8888 từ 450000 VND sang 18.0 USD hoặc chuẩn hóa mã productId viết hoa.
filter() DataStream[T] → DataStream[T]
(Tỷ lệ 1 : 0..1)		 Đánh giá biểu thức điều kiện Boolean cho từng sự kiện; chỉ giữ lại các bản ghi trả về true và loại bỏ ngay các bản ghi trả về false. Giữ lại Order #8888 vì thỏa mãn điều kiện event.amount > 0, loại bỏ các bản ghi lỗi có doanh thu âm hoặc bằng không.
flatMap() DataStream[T] → DataStream[R]
(Tỷ lệ 1 : 0..N)		 Nhận vào một sự kiện và phát ra 0, 1 hoặc nhiều sự kiện đầu ra thông qua bộ thu thập Collector.collect() (kết hợp cả tách dòng lẫn lọc dòng). Tách một giỏ hàng tổng của Order #8888 gồm 3 mặt hàng thành 3 bản ghi dòng chi tiết (OrderLineItem) riêng biệt trên luồng.
keyBy() DataStream[T] → KeyedStream[T, K] Phân vùng logic luồng dữ liệu theo khóa K bằng thuật toán băm kép murmurHash(key) → KeyGroup → TaskSlot, định tuyến qua mạng (Network Shuffle) để mọi sự kiện có cùng khóa luôn chảy về đúng một sub-task vật lý. Gom Order #8888 và mọi giao dịch khác có cùng productId = "PRD-99" về cùng một nhánh thực thi để cộng dồn chính xác.
window() KeyedStream[T, K] → WindowedStream[T, K, W] Cắt luồng đã phân khóa KeyedStream thành các giỏ hữu hạn (Window) dựa trên thời gian hoặc số lượng bản ghi cho từng khóa riêng biệt. Xếp sự kiện Order #8888 (10:00:50) vào giỏ cửa sổ 1 phút [10:00:00, 10:01:00) của riêng khóa "PRD-99".
aggregate() / reduce() WindowedStream → DataStream[R] Cộng dồn cuốn chiếu (Incremental Aggregation) từng sự kiện ngay khi rơi vào cửa sổ thông qua bộ tích lũy Accumulator, tiết kiệm bộ nhớ tối đa. Cộng ngay 450000 của Order #8888 vào tổng doanh thu đang tích lũy của mã "PRD-99" trong khung 10:00–10:01.
union() & connect() Đa luồng → DataStream / ConnectedStreams union() gộp nhiều luồng có cùng kiểu dữ liệu thành một luồng duy nhất (FIFO). connect() nối hai luồng có kiểu dữ liệu khác nhau nhưng dùng chung trạng thái (Shared State) qua CoProcessFunction. union() gộp luồng đơn hàng Web và App; connect() nối luồng giao dịch SalesEvents với luồng quy tắc khuyến mãi động.
process() (KeyedProcessFunction) KeyedStream[T, K] → DataStream[R] Cơ chế cấp thấp nhất cho phép can thiệp vào từng sự kiện qua processElement(), đọc/ghi trực tiếp Keyed State và đặt lịch hẹn giờ ngược qua onTimer(). Khi nhận Order #8888 (CREATED), lưu trạng thái chờ và đặt hẹn giờ cộng thêm 15 phút; nếu tới hạn chưa có sự kiện PAID thì tự động phát cảnh báo hủy đơn.

Tại sao keyBy() gần như luôn phải được gọi trước window()?

Một quy tắc sống còn được nhấn mạnh trên Slide 43 là: phép toán phân khóa keyBy() luôn đi liền trước phép chia cửa sổ window(). Lý do xuất phát từ kiến trúc xử lý song song phân tán của Flink: nếu không gọi keyBy(e -> e.productId) trước, các sự kiện bán hàng của cùng mã sản phẩm "PRD-99" (trong đó có Order #8888) sẽ nằm rải rác ngẫu nhiên trên hàng chục máy chủ TaskManager khác nhau. Khi đó, một phép chia cửa sổ không khóa (windowAll()) buộc phải dồn toàn bộ lưu lượng của cả cụm về một tiến trình duy nhất với độ song song parallelism = 1, gây nghẽn cổ chai lập tức. Ngược lại, khi gọi stream.keyBy(e -> e.productId).window(...), Flink băm khóa "PRD-99" để định tuyến toàn bộ sự kiện của sản phẩm này về cùng một sub-task, cho phép hàng trăm cửa sổ của hàng trăm mã sản phẩm khác nhau được tính toán song song độc lập trên khắp cụm máy chủ.

Giải phẫu KeyedProcessFunction: Khi nào phải lặn xuống đáy tháp?

Dù Table API và Flink SQL giải quyết được phần lớn nhu cầu thống kê, vẫn có những bài toán nghiệp vụ thời gian thực đòi hỏi điều khiển trạng thái tinh vi theo từng mili-giây mà SQL không thể diễn đạt tự nhiên. Khi áp dụng KeyedProcessFunction<K, I, O> trên một KeyedStream, Flink cung cấp cho kỹ sư hai phương thức móc nối (callbacks) kết hợp với đối tượng ngữ cảnh Context và dịch vụ TimerService (Stream Processing with Apache Flink, Ch. 6, tr. 116–121):

  • Phương thức processElement(I value, Context ctx, Collector<O> out): Được kích hoạt ngay khi mỗi sự kiện (như Order #8888) chảy tới toán tử. Tại đây, kỹ sư có thể tra cứu nhãn thời gian của sự kiện qua ctx.timestamp(), kiểm tra Watermark hiện tại qua ctx.timerService().currentWatermark(), cập nhật biến trạng thái cục bộ (ví dụ ValueState<OrderEvent>), và đăng ký một đồng hồ báo thức trong tương lai bằng ctx.timerService().registerEventTimeTimer(timeoutTimestamp).
  • Phương thức onTimer(long timestamp, OnTimerContext ctx, Collector<O> out): Được Flink tự động gọi ngược lại ngay khi Watermark của luồng dữ liệu tiến tới hoặc vượt qua mốc timestamp đã đăng ký. Nhờ cơ chế này, kỹ sư dễ dàng xây dựng máy trạng thái hữu hạn (State Machine) để phát hiện đơn hàng treo quá hạn thanh toán, khử trùng lặp có thời hạn (TTL Deduplication), hoặc đẩy dữ liệu trễ ra luồng phụ Side Output qua ctx.output(OutputTag, value).
# Minh họa PyFlink DataStream API & KeyedProcessFunction xử lý sự kiện Order #8888
from pyflink.common import WatermarkStrategy, Time
from pyflink.common.typeinfo import Types
from pyflink.datastream import StreamExecutionEnvironment
from pyflink.datastream.functions import KeyedProcessFunction, RuntimeContext
from pyflink.datastream.state import ValueStateDescriptor

class UnpaidOrderTimeoutDetector(KeyedProcessFunction):
    def open(self, runtime_context: RuntimeContext):
        # Khởi tạo trạng thái lưu thông tin đơn hàng chờ thanh toán cho từng orderId
        descriptor = ValueStateDescriptor("pending_order", Types.PICKLED_BYTE_ARRAY())
        self.pending_state = runtime_context.get_state(descriptor)

    def process_element(self, event, ctx: KeyedProcessFunction.Context):
        # event: {"orderId": "ORD-8888", "productId": "PRD-99", "amount": 450000, "status": "CREATED"}
        if event["status"] == "CREATED":
            self.pending_state.update(event)
            # Đặt bộ hẹn giờ Event Time: kích hoạt sau 15 phút (900,000 ms) kể từ lúc tạo đơn
            timeout_ts = ctx.timestamp() + 15 * 60 * 1000
            ctx.timer_service().register_event_time_timer(timeout_ts)
        elif event["status"] == "PAID":
            # Nếu khách đã thanh toán trước hạn, xóa trạng thái chờ để hủy cảnh báo
            self.pending_state.clear()

    def on_timer(self, timestamp: int, ctx: KeyedProcessFunction.OnTimerContext):
        # Được gọi tự động khi Watermark vượt mốc timeout_ts mà trạng thái vẫn chưa bị xóa
        unpaid_order = self.pending_state.value()
        if unpaid_order is not None:
            yield f"TIMEOUT_ALERT: Order {unpaid_order['orderId']} ({unpaid_order['amount']} VND) quá hạn 15 phút!"
            self.pending_state.clear()

Trạm 4.2: Nguyên lý Đối ngẫu Luồng – Bảng (Stream-Table Duality), Dynamic Tables & Table API

Nếu tầng DataStream API buộc kỹ sư phải chỉ đạo từng bước cơ học (chọn khóa, mở cửa sổ, viết bộ cộng dồn), thì khi bước lên tầng thứ hai — Table API — cách tiếp cận chuyển hẳn sang tư duy đại số quan hệ. Để thấy rõ sự khác biệt, hãy đặt hai đoạn mã cùng giải quyết một bài toán duy nhất lên bàn cân: tính tổng doanh thu (amount) theo từng mã sản phẩm (productId) trong mỗi cửa sổ lăn 1 phút cho luồng sự kiện chứa Order #8888 (Slide 44):

# 1. Cách tiếp cận DataStream API (Slide 44 — Tầng kiểm soát cơ học: "Engine Room")
stream \
    .key_by(lambda e: e.product_id) \
    .window(TumblingEventTimeWindows.of(Time.minutes(1))) \
    .aggregate(SalesAggregator())

# 2. Cách tiếp cận Table API (Slide 44 — Tầng quan hệ khai báo: "Cockpit")
table \
    .window(Tumble.over(lit(1).minutes).on(col("event_time")).alias("window")) \
    .group_by(col("productId"), col("window")) \
    .select(col("productId"), col("amount").sum.alias("total"))

Chân lý kiến trúc quan trọng nhất từ phép so sánh trên Slide 44 là: Cả hai cách viết đều biên dịch ra cùng một Execution Plan vật lý giống hệt nhau (Both produce the same execution plan!). Khi gửi lên cụm máy chủ Flink, đoạn mã Table API không hề chạy chậm hơn hay tốn bộ nhớ hơn DataStream API; trình tối ưu hóa Flink Planner sẽ tự động dịch chuỗi .group_by().select() thành chính xác các toán tử băm khóa, cửa sổ và bộ cộng dồn trạng thái ở tầng dưới. Sự khác biệt nằm hoàn toàn ở trải nghiệm lập trình viên (developer experience) chứ không phải hiệu năng (not performance): nếu DataStream API là buồng máy (engine room) nơi kỹ sư tự tay vặn từng bánh răng, thì Table API chính là buồng lái hiện đại (cockpit) giúp điều khiển cỗ máy bằng các lệnh quan hệ ngắn gọn, an toàn kiểu dữ liệu.

Cách mỗi sự kiện trên luồng bất biến chuyển hóa thành dòng cập nhật trong Dynamic Table và hội tụ về cùng một Execution Graph.

Giải phẫu Dynamic Table (Bảng động) & Nguyên lý Đối ngẫu Luồng – Bảng (Slide 45)

Làm thế nào Table API và Flink SQL có thể chạy các câu truy vấn quan hệ (vốn được thiết kế cho các bảng tĩnh trong cơ sở dữ liệu) trên một luồng sự kiện vô hạn không có điểm dừng? Câu trả lời nằm ở khái niệm trung tâm Bảng động biến đổi liên tục theo thời gian (Dynamic Table) và nguyên lý Đối ngẫu Luồng – Bảng (Stream-Table Duality) (Slide 45; Streaming Systems, Ch. 6):

  • Từ Luồng sự kiện (Event Stream) sang Bảng động (Dynamic Table): Thay vì nhìn luồng dữ liệu như những gói tin bay qua rồi biến mất, Table API coi luồng sự kiện là nhật ký thay đổi (Changelog) đắp vào một bảng logic đang lớn dần liên tục (continuously changing table). Trên Slide 45, khi sự kiện thứ nhất {id: 1, amount: 100} chảy tới, bảng động có 1 dòng; khi sự kiện thứ hai {id: 2, amount: 200} và sự kiện thứ ba {id: 3, amount: 50} (hay Order #8888: {productId: "PRD-99", amount: 450000}) lần lượt chảy tới, mỗi sự kiện mới tương đương với một phép chèn (+I Insert) làm bảng động SalesEvents bồi đắp thêm dòng mới theo thời gian thực.
  • Truy vấn Liên tục (Continuous Query) trên Bảng động: Khi kỹ sư viết một truy vấn sử dụng các phép toán quan hệ quen thuộc gồm select, filter, join, groupBy trên một Dynamic Table đầu vào, câu truy vấn đó không chạy một lần rồi tắt mà trở thành một Continuous Query chạy mãi mãi. Mỗi khi bảng động đầu vào nhận thêm sự kiện Order #8888, truy vấn liên tục lập tức tính toán lại phần chênh lệch và cập nhật sang một Dynamic Table kết quả ở đầu ra.
  • Từ Bảng động kết quả ngược về Luồng sự kiện (Result Table → Changelog Stream): Để gửi kết quả xuống hệ thống đích (như Kafka hoặc cơ sở dữ liệu), Flink chuyển đổi ngược từng thay đổi trên bảng động kết quả thành luồng sự kiện đầu ra theo hai chế độ: Append-only Stream (chỉ phát bản ghi chèn mới +I, điển hình như kết quả đóng cửa sổ TUMBLE khi Watermark đi qua) hoặc Retract / Upsert Stream (phát cặp bản ghi thu hồi giá trị cũ -U và cập nhật giá trị mới +U đối với các phép GROUP BY không dùng cửa sổ). Nhờ nguyên lý đối ngẫu này, cùng một biểu thức Table API hoạt động đồng nhất trên cả luồng thời gian thực (Streaming) lẫn tập dữ liệu lịch sử hữu hạn (Batch).
Tiêu chí đối chiếu Cơ sở dữ liệu truyền thống / Batch Table Flink Dynamic Table (Streaming Table API & SQL) Ví dụ với luồng SalesEvents & Order #8888
Bản chất dữ liệu nền Tập dữ liệu tĩnh, hữu hạn (Bounded snapshot) đã nằm cố định trên đĩa tại thời điểm bắt đầu chạy truy vấn. Bảng logic biến đổi liên tục (Continuously changing table); mỗi sự kiện mới trên luồng là một bản ghi Insert / Update bồi đắp vào bảng. Khi Order #8888 (PRD-99, 450000) đến lúc 10:00:50, bảng động SalesEvents lập tức tăng thêm 1 dòng mới.
Vòng đời câu truy vấn Chạy một lần duy nhất (Point-in-time query), quét hết bảng, trả về bảng kết quả tĩnh rồi kết thúc tiến trình. Truy vấn liên tục (Continuous Query) không bao giờ tự kết thúc; duy trì State nội bộ để cập nhật kết quả ngay khi có sự kiện mới. Toán tử cộng dồn giữ trạng thái tổng tiền của PRD-99 trong RAM/RocksDB và cộng thêm 450000 ngay khi đọc đơn hàng.
Cơ chế xuất kết quả ra Sink Ghi đè (Overwrite) hoặc nối thêm một lần vào bảng đích khi truy vấn hoàn tất. Phát luồng thay đổi (Changelog Stream) liên tục dưới dạng dòng chỉ thêm (+I Append) hoặc dòng cập nhật thu hồi (-U / +U Retract). Khi Watermark vượt mốc 10:01:00, cửa sổ 1 phút đóng lại và phát bản ghi +I("PRD-99", total_sales) ra Kafka Sink.

Giải phẫu hoàn chỉnh chương trình Table API với DDL và Watermark (Slide 46)

Trong thực tế vận hành, một tác vụ Table API chuẩn mực gồm hai phần tách biệt rõ ràng như minh họa trên Slide 46: (1) Đăng ký siêu dữ liệu bảng nguồn kèm chiến lược Watermark thông qua câu lệnh CREATE TABLE (DDL kết nối trực tiếp tới Kafka topic sales), và (2) Viết chuỗi biểu thức quan hệ đọc từ bảng đó để lọc các đơn hàng hợp lệ (amount > 0) rồi gom nhóm theo sản phẩm:

# Ví dụ hoàn chỉnh Table API đăng ký bảng nguồn Kafka và tính tổng doanh thu (Slide 46)
from pyflink.table import EnvironmentSettings, TableEnvironment
from pyflink.table.expressions import col

env_settings = EnvironmentSettings.in_streaming_mode()
table_env = TableEnvironment.create(env_settings)

# Bước 1: Định nghĩa bảng động SalesEvents gắn với Kafka topic 'sales' và khai báo Watermark trễ 5 giây
table_env.execute_sql("""
    CREATE TABLE SalesEvents (
        productId STRING,
        amount DOUBLE,
        event_time TIMESTAMP(3),
        WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND
    ) WITH (
        'connector' = 'kafka',
        'topic' = 'sales',
        'properties.bootstrap.servers' = 'localhost:9092',
        'format' = 'json'
    )
""")

# Bước 2: Biểu diễn logic nghiệp vụ bằng các toán tử quan hệ của Table API
# Sự kiện Order #8888 (productId="PRD-99", amount=450000, event_time="10:00:50") đi qua bộ lọc amount > 0
sales = table_env.from_path("SalesEvents")
result = sales \
    .filter(col("amount") > 0) \
    .group_by(col("productId")) \
    .select(col("productId"), col("amount").sum.alias("total_sales"))

Trạm 4.3: Động cơ Thực thi Flink SQL, Các Hàm Cửa sổ (TUMBLE, HOP, SESSION) & Phối hợp Đa Tầng API (Interoperability)

Ở đỉnh cao nhất của tháp trừu tượng là Flink SQL — nơi toàn bộ bài toán xử lý luồng thời gian thực được rút gọn thành một câu truy vấn SQL tiêu chuẩn mà bất kỳ ai làm dữ liệu cũng có thể đọc hiểu ngay lập tức. Nhưng đằng sau một câu lệnh SELECT ... GROUP BY tưởng chừng đơn giản đó là cả một dây chuyền biên dịch và tối ưu hóa 5 bước tinh vi trước khi biến thành các tác vụ chạy trên cụm máy chủ (Slide 47):

  1. Bước 1 — Write SQL Query (Viết câu truy vấn SQL): Kỹ sư khai báo logic nghiệp vụ bằng cú pháp chuẩn SQL (ví dụ tính tổng SUM(amount) theo productId và cửa sổ thời gian trên bảng SalesEvents).
  2. Bước 2 — Parse SQL (Phân tích cú pháp & Kiểm tra ngữ nghĩa): Bộ phân tích dựa trên nền tảng Apache Calcite kiểm tra cú pháp câu lệnh SQL, chuyển thành cây cú pháp trừu tượng (Abstract Syntax Tree - AST), sau đó đối chiếu với Catalog để xác thực tên bảng SalesEvents, tên cột productId, kiểu dữ liệu TIMESTAMP(3) và tạo ra kế hoạch logic ban đầu (Logical Plan).
  3. Bước 3 — Optimize Plan (Tối ưu hóa kế hoạch truy vấn): Trình tối ưu hóa của Flink (Flink Optimizer) áp dụng hàng loạt quy tắc đại số quan hệ và ước lượng chi phí (như đẩy bộ lọc WHERE amount > 0 xuống sát nguồn đọc Kafka — Predicate Pushdown, loại bỏ các cột không dùng đến — Projection Pruning, sắp xếp lại thứ tự phép nối) để tạo ra kế hoạch vật lý tối ưu nhất.
  4. Bước 4 — Create Execution Plan (Sinh mã & Dịch sang đồ thị thực thi): Flink Planner cùng bộ sinh mã trực tiếp (Janino Code Generation) biên dịch kế hoạch đã tối ưu thành các toán tử thực thi cấp thấp (StreamGraph → JobGraph → ExecutionGraph), hoàn toàn tương đương với đồ thị sinh ra từ Table API hay DataStream API.
  5. Bước 5 — Run on Flink Runtime (Thực thi phân tán trên cụm Flink): Đồ thị thực thi được triển khai xuống các TaskSlot của TaskManager để tiêu thụ luồng sự kiện Order #8888 với đầy đủ cơ chế quản lý trạng thái và chịu lỗi Checkpointing.
Kiến trúc lai kết hợp sức mạnh tùy biến cấp thấp của DataStream API với sự cô đọng của Table API và Flink SQL trong cùng một Job.

Ba hàm cửa sổ thời gian tích hợp sẵn trong Flink SQL (Slide 48–49)

Để gom nhóm luồng sự kiện vô hạn theo các khung thời gian mà chúng ta đã học ở Chặng 3, Flink SQL cung cấp sẵn 3 hàm cửa sổ trực tiếp trong mệnh đề GROUP BY (hoặc cú pháp hàm trả về bảng Windowing TVF trong chuẩn Flink mới). Điều kiện tiên quyết bắt buộc được cảnh báo trên Slide 49 là: bảng nguồn bắt buộc phải có mệnh đề khai báo WATERMARK FOR trên cột thời gian sự kiện thì các hàm cửa sổ Event Time dưới đây mới có thể kích hoạt và đóng cửa sổ:

Hàm cửa sổ trong Flink SQL (Slide 48) Cú pháp chuẩn & Ý nghĩa tham số Bản chất cơ học của cửa sổ Trường hợp sử dụng thực tế (Use Case)
TUMBLE
(Cửa sổ lăn cố định)		 TUMBLE(time_col, INTERVAL '1' MINUTE)
Tham số: cột thời gian time_col và độ rộng cửa sổ size.		 Chia trục thời gian thành các khung có kích thước cố định, nối đuôi nhau và không bao giờ chồng lấp. Mỗi sự kiện (như Order #8888 lúc 10:00:50) chỉ thuộc về duy nhất 1 cửa sổ [10:00, 10:01). Báo cáo doanh thu theo từng phút hoặc từng giờ (Hourly sales report), chốt sổ giao dịch định kỳ không trùng lặp.
HOP
(Cửa sổ trượt chồng lấp)		 HOP(time_col, INTERVAL '30' SECOND, INTERVAL '1' MINUTE)
Tham số 1 sau cột giờ là bước trượt slide (30s); tham số 2 là độ rộng cửa sổ size (1m).		 Cửa sổ có độ rộng cố định 1 phút nhưng cứ mỗi 30 giây lại trượt sang mở một cửa sổ mới. Do slide < size, các cửa sổ chồng lấp lên nhau và sự kiện Order #8888 được tính trong 2 cửa sổ liên tiếp. Tính trung bình trượt làm mượt đường biểu đồ (Rolling average), phát hiện xu hướng tăng đột biến đơn hàng trong 1 phút gần nhất cập nhật mỗi 30 giây.
SESSION
(Cửa sổ phiên động)		 SESSION(time_col, INTERVAL '5' MINUTE)
Tham số: cột thời gian time_col và khoảng lặng tối đa inactivity gap (5m).		 Không có độ dài cố định và không căn theo mốc đồng hồ tròn; tự động gom các sự kiện diễn ra liên tiếp và chỉ đóng phiên khi không có sự kiện mới nào xuất hiện quá khoảng lặng 5 phút. Phân tích hành vi người dùng theo phiên truy cập (User session analytics), đo tổng giá trị giỏ hàng trong một đợt lướt ứng dụng liên tục. 
-- Truy vấn Flink SQL tính tổng doanh thu mỗi phút theo sản phẩm và gắn mốc đầu/cuối cửa sổ (Slide 49)
-- Lưu ý bắt buộc: Bảng SalesEvents phải được định nghĩa kèm WATERMARK FOR event_time trước đó!
SELECT
    productId,
    TUMBLE_START(event_time, INTERVAL '1' MINUTE) AS window_start,
    TUMBLE_END(event_time, INTERVAL '1' MINUTE)   AS window_end,
    SUM(amount) AS total_sales
FROM SalesEvents
WHERE amount > 0
GROUP BY
    productId,
    TUMBLE(event_time, INTERVAL '1' MINUTE);

Trong câu truy vấn trên Slide 49, khi sự kiện Order #8888 (productId = "PRD-99", amount = 450000, event_time = "10:00:50") đi qua bộ lọc WHERE amount > 0, nó được gom vào nhóm khóa "PRD-99" của cửa sổ TUMBLE 1 phút. Hai hàm phụ trợ TUMBLE_START(...) và TUMBLE_END(...) trích xuất chính xác hai đầu mút của khung thời gian đó (window_start = 10:00:00.000 và window_end = 10:01:00.000) để xuất ra bản ghi kết quả hoàn chỉnh ngay khi Watermark vượt qua mốc 10:01:00.

Phối hợp Đa tầng API trong cùng một Flink Job — API Interoperability (Slide 50)

Trong các dự án thực chiến, kỹ sư hiếm khi chỉ dùng độc quyền một tầng API duy nhất từ đầu tới cuối. Chẳng hạn: đầu vào cần đọc luồng sự kiện thô từ Kafka kèm logic lọc dữ liệu hỏng và gán Watermark tùy biến phức tạp (thế mạnh của DataStream API); phần lõi ở giữa cần tính tổng doanh thu theo cửa sổ 1 phút một cách ngắn gọn, dễ đọc (thế mạnh của Table API & Flink SQL); và đầu ra lại cần đẩy kết quả xuống một hệ thống cảnh báo hoặc custom_sink đặc thù (thế mạnh của DataStream API). Điểm ưu việt của Apache Flink là cho phép chuyển đổi qua lại liền mạch giữa cả 3 tầng API trong cùng một chương trình mà không tốn chi phí tuần tự hóa thừa (Slide 50 — Mixing APIs in One Job):

# Kịch bản phối hợp cả 3 tầng API (DataStream ↔ Table API ↔ Flink SQL) trong cùng 1 Flink Job (Slide 50)

# Step 1: Dùng DataStream API để đọc nguồn tùy biến (Custom Source) và gán chiến lược Watermark phức tạp
stream = env.from_source(kafka_source, watermark_strategy, "Kafka")

# Step 2: Dùng Table API để cầu nối chuyển đổi luồng DataStream thành đối tượng Dynamic Table có Schema rõ ràng
table = table_env.from_data_stream(
    stream,
    Schema.new_builder()
        .column("productId", DataTypes.STRING())
        .column("amount", DataTypes.DOUBLE())
        .column("event_time", DataTypes.TIMESTAMP(3))
        .watermark("event_time", "event_time - INTERVAL '5' SECOND")
        .build()
)

# Step 3: Dùng Flink SQL để thực hiện phép gom nhóm cửa sổ TUMBLE 1 phút cực kỳ ngắn gọn và dễ bảo trì
table_env.create_temporary_view("SalesEvents", table)
result = table_env.sql_query("""
    SELECT productId, SUM(amount) AS total_sales
    FROM SalesEvents
    GROUP BY productId, TUMBLE(event_time, INTERVAL '1' MINUTE)
""")

# Step 4: Chuyển bảng kết quả Dynamic Table ngược trở lại thành DataStream để đẩy ra Custom Sink
output_stream = table_env.to_data_stream(result)
output_stream.sink_to(custom_sink)

Khung quyết định lựa chọn tầng API cho Kỹ sư Dữ liệu

Để tránh hai thái cực sai lầm — hoặc lạm dụng KeyedProcessFunction viết hàng trăm dòng code thủ công cho một phép cộng dồn đơn giản, hoặc cố ép Flink SQL giải quyết các bài toán máy trạng thái nhiều bước — bảng dưới đây tổng kết ma trận quyết định chọn tầng API theo đúng bản chất bài toán:

Tầng API trong Flink Trừu tượng dữ liệu trung tâm Quyền kiểm soát State & Timer Khi nào nên chọn làm công cụ chính?
Flink SQL Bảng động (Dynamic Table) khai báo qua DDL và truy vấn bằng chuẩn ANSI SQL. Hoàn toàn tự động (Managed by Planner); người dùng không chạm trực tiếp vào biến State hay Timer. Các bài toán ETL thời gian thực, lọc dòng, làm giàu dữ liệu (Lookup/Interval Join), thống kê gom nhóm theo cửa sổ TUMBLE, HOP, SESSION.
Table API Đối tượng Table trong Python/Java/Scala với chuỗi hàm quan hệ có kiểm tra kiểu. Hoàn toàn tự động (chia sẻ chung bộ tối ưu hóa Calcite và sinh cùng một Execution Plan với Flink SQL). Khi cần xây dựng các đường ống biến đổi quan hệ có tính mô-đun hóa cao, truyền tham số động bằng code và kiểm thử đơn vị (Unit Test) từng hàm.
DataStream API & ProcessFunction Luồng sự kiện bất biến DataStream<T> và luồng phân khóa KeyedStream<T, K>. Kiểm soát thủ công toàn diện từng sự kiện (processElement), trạng thái thô (ValueState, MapState) và bộ hẹn giờ (onTimer). Khi cần xây dựng máy trạng thái nghiệp vụ phức tạp (như phát hiện đơn hàng Order #8888 quá hạn 15 phút), định tuyến đa luồng phụ (Side Outputs), hoặc tích hợp Source/Sink tùy chỉnh.

Tóm tắt bỏ túi Chặng 4 & Checklist 5 câu hỏi bản chất

Checklist 5 câu hỏi bản chất kiểm tra độ hiểu sâu Chặng 4 (Hệ sinh thái Flink APIs & Interoperability):

  1. Tháp trừu tượng 3 tầng API của Flink: Sự đánh đổi cốt lõi khi đi từ đỉnh tháp (Flink SQL → Table API) xuống đáy tháp (DataStream API / ProcessFunction) là gì? Khi nào kỹ sư bắt buộc phải sử dụng KeyedProcessFunction thay vì SQL?
    Đáp án: Đi lên đỉnh tháp mang lại năng suất lập trình cao nhất (higher productivity) với cú pháp khai báo ngắn gọn; đi xuống đáy tháp mang lại quyền kiểm soát cấp thấp chi tiết nhất (lower-level control) trên từng sự kiện. Kỹ sư phải dùng KeyedProcessFunction khi bài toán đòi hỏi thao tác trực tiếp trên Keyed State và đăng ký bộ hẹn giờ TimerService (onTimer) cho các kịch bản máy trạng thái hoặc cảnh báo quá hạn mà SQL không diễn đạt được.
  2. Quy tắc vàng keyBy() trước window() trong DataStream API: Tại sao khi tính tổng doanh thu theo cửa sổ cho sự kiện Order #8888 (productId = "PRD-99"), phép biến đổi keyBy() gần như luôn phải được gọi ngay trước window()?
    Đáp án: Vì trong môi trường phân tán, các sự kiện của cùng một mã sản phẩm "PRD-99" ban đầu nằm rải rác trên nhiều tiến trình khác nhau. Gọi keyBy(e -> e.productId) giúp Flink băm khóa để định tuyến mọi sự kiện có chung productId về cùng một sub-task vật lý, nhờ đó các cửa sổ thời gian của từng sản phẩm được gom nhóm chính xác và tính toán song song trên toàn cụm.
  3. So sánh hiệu năng giữa DataStream API và Table API: Cùng một bài toán cộng dồn doanh thu cửa sổ 1 phút, viết bằng Table API có chạy chậm hơn viết thủ công bằng DataStream API không? Khái niệm Dynamic Table giúp thống nhất xử lý luồng và xử lý lô như thế nào?
    Đáp án: Hoàn toàn không chậm hơn — cả hai cách viết đều được bộ tối ưu hóa của Flink biên dịch ra cùng một kế hoạch thực thi vật lý (same execution plan); sự khác biệt nằm ở trải nghiệm lập trình viên (buồng lái cockpit so với buồng máy engine room) chứ không phải hiệu năng. Khái niệm Dynamic Table xem luồng sự kiện đang chảy như một bảng logic biến đổi liên tục (mỗi sự kiện mới là một phép chèn/cập nhật vào bảng), cho phép chạy cùng các toán tử quan hệ select, filter, join, groupBy trên cả dữ liệu vô hạn lẫn hữu hạn.
  4. Chu trình 5 bước của Flink SQL & Ba hàm cửa sổ thời gian: Một câu truy vấn Flink SQL đi qua 5 bước nào để chạy trên cụm? Sự khác biệt giữa 3 hàm TUMBLE, HOP, SESSION là gì và điều kiện tiên quyết nào trên bảng nguồn giúp chúng hoạt động theo Event Time?
    Đáp án: Chu trình 5 bước gồm: Write SQL Query → Parse SQL → Optimize Plan → Create Execution Plan → Run on Flink Runtime. Hàm TUMBLE(time_col, size) tạo cửa sổ cố định không chồng lấp; HOP(time_col, slide, size) tạo cửa sổ trượt chồng lấp (chú ý tham số slide đứng trước size); và SESSION(time_col, gap) tạo cửa sổ động đóng theo khoảng lặng. Điều kiện bắt buộc là bảng nguồn phải khai báo mệnh đề WATERMARK FOR event_time AS ... trong DDL.
  5. Phối hợp đa tầng API (API Interoperability): Làm thế nào để kết hợp cả DataStream API, Table API và Flink SQL trong cùng một tác vụ xử lý luồng SalesEvents?
    Đáp án: Kỹ sư thực hiện quy trình 4 bước liên thông: (1) Dùng env.from_source(...) ở DataStream API để đọc Kafka kèm chiến lược Watermark tùy chỉnh; (2) Dùng table_env.from_data_stream(stream, Schema...) để chuyển luồng thành bảng động; (3) Đăng ký view tạm bằng create_temporary_view và chạy truy vấn cửa sổ bằng table_env.sql_query(...); cuối cùng (4) Dùng table_env.to_data_stream(result) chuyển bảng kết quả ngược lại thành DataStream để ghi ra custom_sink.
