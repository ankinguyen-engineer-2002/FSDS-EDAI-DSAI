Khi bộ nhớ RAM quá đắt (~$10/GB) và mất sạch dữ liệu ngay khi cúp điện, Đơn hàng #8888 sau khi sinh ra từ hệ thống bán hàng (OLTP) bắt buộc phải được chuyển sang kho lưu trữ bền vững giá rẻ. Tại tầng này, kiến trúc sư dữ liệu phải giải quyết 4 quyết định thiết kế: chọn mô hình kho lưu trữ (File Storage, Block Storage hay Object Storage), chọn bố cục tuần tự hóa trên đĩa (Row: CSV, JSONL, Avro hay Columnar: Parquet, ORC), chọn chuẩn bộ nhớ trong RAM xuyên ngôn ngữ (Apache Arrow), và chọn thuật toán nén bảo toàn tính phân tách (Splittability với Snappy, ZSTD, Gzip, Bzip2).

Trạm 2.1: Bộ ba mô hình lưu trữ cơ sở — File vs. Block vs. Object storage

Khi dữ liệu nhị phân của Đơn hàng #8888 được lưu xuống các cụm máy chủ, có 3 mô hình tổ chức vật lý và logic hoàn toàn khác nhau:

Đối chiếu kiến trúc cây thư mục phân cấp (File), khối byte cố định (Block) và không gian phẳng định danh qua Key-Value (Object).
  • File Storage (NTFS/ext4, NAS/NFS/SMB): Lưu cây thư mục phân cấp (directory tree) kèm quyền truy cập, con trỏ thư mục và nhật ký phục hồi (journaling). Khi tích lũy hàng chục triệu tệp hóa đơn, bảng chỉ mục inode table và khóa đường dẫn (path traversal locks) bị quá tải, không thể mở rộng cho Big Data.
  • Block Storage (SAN, AWS EBS, Local NVMe Instance Store): Chia dữ liệu thành khối cố định (4KB–512KB) cho độ trễ < 1 ms. Trên đám mây có 2 nhánh: Virtualized Network Block (AWS EBS) nhân bản trong cùng 1 Availability Zone (tới 64 TiB, 256.000 IOPS, 4.000 MiB/s, hỗ trợ Point-in-time Differential Snapshots xuống S3) và Local Instance Store (NVMe) làm bộ đệm tạm (mất sạch khi dừng VM). Lý tưởng cho OLTP DB / VM nhưng đắt đỏ và không thể chia sẻ song song xuyên cụm.
  • Cloud Object Storage (Amazon S3 / Azure Blob & ADLS / GCS): Dịch vụ serverless hoạt động như kho key-value phẳng trong Bucket. Mỗi Object gồm 3 thành phần: (1) ID (Object Key như orders/8888.parquet — dấu / chỉ là tên chuỗi phẳng), (2) Metadata tùy biến không giới hạn, và (3) Data (chuỗi byte nhị phân truy cập qua HTTP REST API PUT/GET, tự động băm và rải qua nhiều Availability Zones).

Triết lý "Less is More" & Quản trị Vòng đời Object Storage

Chính việc lược bỏ khả năng sửa tại chỗ (Immutability) và cây thư mục vật lý lại tạo nên sức mạnh quy mô đám mây của Object Storage:

Đánh đổi tính bất biến (Immutability) và độ trễ ~100 ms để loại bỏ cơ chế khóa tệp, đạt băng thông song song ~3 GB/s, tách rời Compute – Storage và quản trị vòng đời dữ liệu qua Storage Classes.
  • Lưu ý vận hành thực tế: Dù Object Storage hỗ trợ đọc một phần tệp qua HTTP Range Requests (để đọc riêng Footer của Parquet) và đảm bảo Strong Read-After-Write Consistency, tính năng Object Versioning lưu bản sao nguyên khối (brute-force full copy) cho mỗi lần ghi đè (khác với Differential Snapshot của EBS) nên bắt buộc phải đi kèm Lifecycle Policies hạ cấp sang Standard-IA, One Zone-IA hoặc Glacier Deep Archive (~$1/TB/tháng).

Trạm 2.2: Định dạng tệp & tuần tự hóa (Serialization) — Row (CSV, Avro) vs. columnar (Parquet, ORC)

Dữ liệu trong bộ nhớ phần mềm tồn tại dưới dạng các đối tượng nối nhau bằng con trỏ, không thể ghi nguyên trạng xuống đĩa hay truyền qua mạng. Quá trình làm phẳng (flattening) và đóng gói cấu trúc dữ liệu thành chuỗi byte tiêu chuẩn được gọi là Tuần tự hóa (Serialization), chia thành hai trường phái bố trí vật lý trên đĩa: Theo hàng (Row-oriented) và Theo cột theo phân đoạn (Column-oriented / Columnar):

Bố trí nối tiếp từng bản ghi theo hàng (tối ưu ghi luồng/đọc trọn dòng) so với xoay dọc theo từng cột trong Row Group (tối ưu quét phân tích và nén).

Định dạng theo Hàng (Row-Oriented: CSV, JSONL, Apache Avro)

  • Văn bản thô (CSV, JSON, XML) vs. JSON Lines (JSONL): Định dạng theo hàng tối ưu khi đọc trọn vẹn một bản ghi hoặc ghi nối đuôi luồng sự kiện. Tuy nhiên, CSV thiếu schema chặt chẽ, dễ lỗi ký tự thoát và tốn CPU phân tách chuỗi (parse overhead); còn JSONL (mỗi dòng 1 đối tượng JSON ngăn bởi \n) phù hợp làm bước đệm thu thập REST API trước khi chuyển sang dạng nhị phân/cột.
  • Chuẩn nhị phân theo hàng Apache Avro: Nhúng trực tiếp Schema JSON ở phần Header (Self-describing, hỗ trợ Schema Evolution) và mã hóa dữ liệu thành nhị phân (binary) nhỏ gọn. Đặc biệt, Avro chèn các mốc đồng bộ Sync Markers 16-byte giữa các khối giúp tệp vừa chia nhỏ đọc song song được (splittable), vừa phục hồi an toàn đến mốc Sync Marker gần nhất nếu luồng ghi Streaming / Kafka / CDC bị sập nguồn giữa chừng.

Định dạng theo Cột (Columnar-Oriented: Apache Parquet & Apache ORC)

Khi truy vấn thống kê chỉ cần tính tổng cột Amount trên 10 triệu đơn hàng, định dạng theo hàng (CSV/Avro) buộc ổ đĩa phải đọc lướt qua toàn bộ các cột không liên quan. Định dạng theo cột (Apache Parquet và Apache ORC) giải quyết triệt để bằng cách chia bảng thành các phân đoạn hàng (Row Groups), sau đó xoay trục dữ liệu và đóng gói riêng từng cột:

Động cơ truy vấn (Spark/Trino/DuckDB) luôn đọc phần Footer Metadata ở đáy tệp trước tiên để cắt tỉa cột (Column Pruning) và nhảy cóc qua các Row Group không khớp điều kiện lọc (Data Skipping).
  • 3 Vũ khí cốt lõi của Parquet & Thuật toán Google Dremel: (1) Column Pruning đọc đúng Byte Offset của các cột cần thiết (giảm 80–95% I/O); (2) Nén chuyên biệt theo cột nhờ Dictionary Encoding, Run-Length Encoding (RLE) và Delta Encoding; (3) Data Skipping / Predicate Pushdown nhảy bỏ qua cả Row Group dựa vào thống kê Min / Max / Null Count ở Footer; kết hợp thuật toán Google Dremel (dùng Definition Levels và Repetition Levels) để ép phẳng JSON lồng nhau thành các cột độc lập.
  • Đánh đổi của định dạng cột & Mô hình Hybrid Serialization: Parquet tốn RAM giữ đệm Row Group (128MB–1GB), hỏng tệp nếu sập nguồn trước khi ghi Footer, và cực đắt khi sửa lẻ 1 dòng; so với Apache ORC, Parquet được hỗ trợ rộng rãi hơn trên Cloud (Snowflake/BigQuery hỗ trợ cả import và export Parquet). Để vừa ghi luồng nhanh vừa quét cột nhanh, các bảng Lakehouse (Hudi, Iceberg) áp dụng Tuần tự hóa Lai (Hybrid Serialization): bắt luồng cập nhật vào tệp dòng Avro rồi định kỳ Compaction sang tệp cột Parquet.

Trạm 2.3: Tuần tự hóa trong bộ nhớ (In-Memory Serialization) — Apache Arrow

Khi tệp Parquet chứa Đơn hàng #8888 đã được đọc từ S3 lên RAM của Apache Spark (JVM) và cần truyền sang thư viện Python (Pandas / PyArrow / ML) trên cùng máy chủ: trước đây, vì mỗi ngôn ngữ sắp xếp byte trong RAM một kiểu, CPU lãng phí tới 70–80% thời gian chỉ để Serialize / Deserialize và chép lại vùng nhớ. Apache Arrow giải quyết triệt để bằng cách thống nhất một bố cục bộ nhớ cột duy nhất trên RAM cho mọi ngôn ngữ (C, C++, Go, Java, Python, R, Rust):

Apache Arrow thống nhất một bố cục bộ nhớ cột duy nhất trên RAM, cho phép Spark (JVM), Python (Pandas/Polars) và C++/Rust đọc chung vùng nhớ qua con trỏ mà không tốn CPU dịch lại.
  • Cơ chế Zero-copy, Shredding & Virtual Memory (mmap): Các tiến trình khác ngôn ngữ chỉ cần truyền con trỏ địa chỉ RAM để đọc trực tiếp dữ liệu (Zero-copy) và ép phẳng JSON lồng nhau thành mảng cột trong bộ nhớ (Shredding). Vì định dạng nhị phân của Arrow dùng chung cho cả RAM, mạng (Arrow Flight) và đĩa, hệ điều hành có thể dùng Virtual Memory (mmap) ánh xạ thẳng tệp từ đĩa vào không gian địa chỉ với Zero Deserialization Overhead — nền tảng tốc độ của Dremio, DuckDB, Polars và Spark Pandas UDF.

Trạm 2.4: Kỹ thuật nén dữ liệu (Compression) & cạm bẫy tính phân tách (Splittability)

Trong kỹ thuật dữ liệu phân tích, hệ thống bắt buộc dùng nén không mất dữ liệu (Lossless compression — mã hóa các chuỗi dư thừa lặp lại đạt tỷ lệ 2:1 đến 10:1 rồi khôi phục chính xác từng bit khi đọc, thay vì nén mất dữ liệu Lossy như JPEG/MP3). Hiệu ứng khuếch đại phần cứng khi nén cột Parquet/ZSTD: giảm dung lượng đĩa 4–10 lần, tăng tốc độ quét đĩa hiệu dụng từ 200 MB/s lên 800 MB/s – 2 GB/s, và nhân băng thông mạng 10 Gbps lên tương đương 100 Gbps.

Mỗi thuật toán nén là một sự đánh đổi giữa Tỷ lệ nén (Không gian lưu trữ & I/O) và Chi phí thời gian/tài nguyên của CPU (Tốc độ nén & giải nén):

Tính phân tách (Splittability) khi xử lý Phân tán

Khi cụm 100 máy chủ tính toán (Apache Spark hoặc Hadoop) cùng đọc một tệp dữ liệu 100 GB, điều kiện tiên quyết là tệp đã nén đó phải chia nhỏ được (Splittable) để 100 máy cùng đọc song song các phân đoạn độc lập:

Nén nguyên tệp bằng Gzip (orders.csv.gz) biến tệp 100 GB thành một khối không thể cắt giữa chừng; trong khi Parquet và Avro chia dữ liệu thành các khối độc lập (Row Groups / Sync Markers) rồi mới nén từng khối.
  • Tại sao Parquet và Avro giải quyết triệt để bài toán Splittability? Vì chúng là các Container Formats (Định dạng đóng gói theo thùng chứa): thay vì lấy thuật toán nén bọc bên ngoài toàn bộ tệp lớn, chúng chia dữ liệu bên trong thành từng khối độc lập (Row Groups / Data Pages trong Parquet kèm mục lục Byte Offset ở Footer, hoặc các khối ngăn cách bởi Sync Markers 16-byte trong Avro) rồi mới nén riêng từng khối đó bằng Snappy hoặc ZSTD. Nhờ vậy, hàng trăm máy chủ có thể dùng HTTP Range Requests nhảy thẳng tới bất kỳ khối nào giữa tệp để đọc và giải nén song song cùng lúc!

Tóm tắt bỏ túi Chặng 2 (4 Quyết định thiết kế lưu trữ)

  1. Chọn Mô hình Kho (Storage Model): Để lưu trữ lâu dài hàng chục triệu đơn hàng như Đơn #8888 với chi phí rẻ (~$0.02/GB/tháng) và mở rộng vô hạn, chọn Cloud Object Storage (S3/ADLS/GCS) thay cho File Storage và Block Storage — chấp nhận tính bất biến (Immutability) để đổi lấy băng thông đọc/ghi song song không khóa (lock-free) và tách rời Compute khỏi Storage.
  2. Chọn Định dạng Luồng / Hàng (Row Serialization): Để truyền dữ liệu luồng (Streaming / Kafka / CDC) an toàn và chịu lỗi mất điện, đóng gói nhị phân theo hàng bằng Apache Avro (nhúng JSON Schema ở Header và chèn Sync Markers 16-byte).
  3. Chọn Định dạng Phân tích / Cột (Columnar Serialization & Compression): Để lưu trữ phân tích trên Object Storage, xoay dọc dữ liệu sang Apache Parquet nén bằng Snappy / ZSTD — kết hợp cắt tỉa cột (Column Pruning), nhảy cóc qua Row Group nhờ thống kê Footer Min/Max (Data Skipping), ép phẳng JSON lồng nhau bằng Google Dremel, và giữ nguyên tính phân tách (Splittability).
  4. Chọn Chuẩn Bộ nhớ Trong RAM (In-Memory Serialization): Khi bốc dữ liệu lên RAM để tính toán xuyên ngôn ngữ (Spark JVM → Python Pandas/ML/C++), dùng chuẩn bộ nhớ cột Apache Arrow để đọc trực tiếp Zero-copy mà không tốn CPU dịch lại.
