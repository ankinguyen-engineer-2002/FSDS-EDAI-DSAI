Từ Đầm lầy Dữ liệu Data Swamp (Chặng 5) đến Lớp Siêu dữ liệu Giao dịch của Data Lakehouse (Chặng 6)

Ở Chặng 5, khi một tác vụ Spark đứt mạng giữa chừng để lại tệp rác ghi dở 3.parquet nằm cạnh tệp chạy lại 3_v2.parquet trên S3, chuẩn bảng thư mục kiểu cũ cộng trùng doanh thu của Đơn hàng #8888 gấp đôi. Chặng 6 giải quyết tận gốc bài toán này bằng cách đặt một lớp Transactional Metadata (Open Table Formats: Delta Lake, Apache Iceberg, Apache Hudi) ngay phía trên các tệp Parquet bất biến của Cloud Object Storage.

Trạm 6.1: Kiến trúc Data Lakehouse & bước ngoặt "Định nghĩa lại một bảng"

Hợp nhất Data Warehouse + Data Lake = Data Lakehouse

Thuật ngữ Lakehouse được chuẩn hóa bởi Michael Armbrust và các cộng sự trong bài báo "Lakehouse: A New Generation of Open Platforms That Unify Data Warehousing and Advanced Analytics" (CIDR 2021), hợp nhất kỷ luật giao dịch của Data Warehouse với chi phí và tính mở của Data Lake:

Sự hợp nhất giữa kỷ luật quản trị, giao dịch ACID và tốc độ truy vấn BI của Data Warehouse với chi phí lưu trữ siêu rẻ (~$0.02/GB/tháng), định dạng mở và khả năng phục vụ AI/ML của Data Lake.
  • Tiến hóa 3 Thế hệ Nền tảng Dữ liệu (CIDR 2021 & Delta Lake: The Definitive Guide): Thế hệ 1 (Data Warehouse) gắn chặt Compute-Storage đắt đỏ và mù dữ liệu phi cấu trúc; Thế hệ 2 (Two-Tier: Data Lake + Warehouse) mắc 4 căn bệnh hệ thống (ETL hai chặng dễ gãy, dữ liệu bị trễ Stale data, ML/PyTorch không đọc trực tiếp được Warehouse, và TCO đội gấp đôi do lưu trùng lặp); Thế hệ 3 (Data Lakehouse) đặt trực tiếp tầng giao dịch ACID lên trên Apache Parquet / S3, xóa bỏ hoàn toàn việc chép dữ liệu sang kho thứ hai.

Kiến trúc 3 Tầng của Lakehouse & Nguyên lý Tách rời Compute – Storage

Lakehouse tách biệt hoàn toàn Tầng tính toán (Compute) và Tầng lưu trữ (Storage), đồng thời chèn thêm Tầng giao dịch (Transaction Layer) ở chính giữa:

Kiến trúc 3 tầng chuẩn của một hệ thống Data Lakehouse: (1) Query Engines / Ephemeral Compute có bộ đệm cục bộ, (2) Transaction & Table Format Layer đảm nhận ACID và Table Services, (3) Cloud Object Storage lưu trữ Data Files (Parquet/ORC/Avro) và Metadata Files.
  • Tách rời Compute – Storage & 3 Vũ khí Tăng tốc BI (CIDR 2021): Đơn hàng #8888 nằm trên S3 giá rẻ (~$0.02/GB/tháng), còn các cụm Ephemeral Clusters chỉ bật khi chạy job. Dù S3 có độ trễ ~100 ms, Lakehouse vẫn đạt tốc độ BI ngang ngửa Data Warehouse nhờ 3 trụ cột: (1) Hot Data Caching trên NVMe SSD/RAM cục bộ của nút tính toán, (2) Auxiliary Data & Layout (Min/Max, Bloom Filter, gom cụm Z-Order / Hilbert Curve) giúp bỏ qua 95–99% tệp (Data Skipping), và (3) Vectorized Execution (Photon, Velox, DuckDB, Trino) xử lý cột trên Apache Arrow bằng lệnh phần cứng SIMD.
  • Phân biệt File Format vs. Table Format & Bước ngoặt khỏi Hive: File Format (Parquet, Avro, ORC) quy định cách mã hóa byte bên trong 1 tệp đơn lẻ; còn Table Format (Delta Lake, Iceberg, Hudi) quản lý hàng nghìn tệp riêng lẻ như một bảng logic có ACID. Khác với Apache Hive Table Format định nghĩa bảng bằng toàn bộ nội dung thư mục (dẫn đến đọc nhầm tệp rác 3.parquet và nghẽn lệnh S3 LIST), bộ ba Open Table Formats định nghĩa bảng bằng danh sách chuẩn tắc các tệp hợp lệ (canonical list of files) trong Metadata!

Trạm 6.2: Giải phẫu "Bộ não" Của bộ ba Open Table Formats (Delta Lake, Iceberg, Hudi)

Cùng quản lý danh sách tệp Parquet hợp lệ trên Object Storage, nhưng Delta Lake, Apache Iceberg và Apache Hudi tổ chức cấu trúc siêu dữ liệu theo 3 cơ chế kiến trúc khác biệt:

Delta Lake: Nhật ký giao dịch tuần tự _delta_log

Mọi giao dịch thay đổi bảng trong Delta Lake đều ghi nối đuôi một tệp JSON 20 chữ số tuần tự (000000.json, 000001.json...) trong thư mục _delta_log/:

Cơ chế nhật ký giao dịch tuần tự _delta_log của Delta Lake: mọi truy vấn đều đối chiếu danh sách tệp hợp lệ từ tệp Checkpoint và các tệp JSON commit, khiến tệp ghi dở 3_zombie_partial.parquet tự động tàng hình 100%.
  • Giải phẫu 6 loại Action trong JSON & Cơ chế _last_checkpoint (Delta Lake: The Definitive Guide, tr. 36–45): Mỗi tệp commit JSON chứa 6 loại bản ghi hành động: (1) protocol (minReaderVersion / minWriterVersion), (2) metaData (schema, partitionColumns, cấu hình bảng), (3) add (đăng ký tệp Parquet mới hợp lệ kèm stats: numRecords, minValues, maxValues, nullCount cho 32 cột đầu), (4) remove (bản ghi bia mộ tombstone gỡ tệp cũ khỏi bản hiện hành nhưng giữ tệp vật lý cho Time Travel kèm deletionTimestamp), (5) commitInfo (nhật ký kiểm toán), và (6) cdc (trỏ tới _change_data). Cứ sau mỗi 10 commits, Delta Lake tự động gộp trạng thái từ đầu bảng thành tệp .checkpoint.parquet (hỗ trợ cả V2 Checkpoints với sidecar Parquet) và cập nhật con trỏ _last_checkpoint để động cơ đọc nhảy thẳng tới mốc gần nhất mà không cần quét lại hàng vạn tệp JSON cũ!

Apache Iceberg: Cây Siêu dữ liệu 3 Tầng (3-Layer Metadata Tree)

Iceberg quản lý bảng quy mô Petabyte qua cây siêu dữ liệu phân cấp 3 tầng từ Catalog → Metadata File (.json) → Manifest List (.avro) → Manifest Files (.avro):

Cấu trúc cây siêu dữ liệu phân cấp của Apache Iceberg: Iceberg Catalog (giữ con trỏ nguyên tử CAS) → Tầng 1: Metadata File (.metadata.json) → Tầng 2: Manifest List (.avro) → Tầng 3: Manifest Files (.avro) → Data & Delete Files (.parquet).
  • Tráo con trỏ Nguyên tử (Atomic CAS Swap) & Cắt tỉa Siêu dữ liệu 2 Cấp (Apache Iceberg: The Definitive Guide, tr. 51–68): Mọi giao dịch Iceberg hoàn tất bằng một phép hoán đổi nguyên tử (Compare-And-Swap — CAS) tại tầng Catalog (REST Catalog, Nessie, Unity Catalog, Snowflake Polaris, Glue) đổi con trỏ từ v1.metadata.json sang v2.metadata.json, đồng thời tái sử dụng các Manifest file cũ không thay đổi. Khi truy vấn Đơn #8888, Iceberg cắt tỉa 2 cấp ngay trên Metadata: Cấp 1 (Manifest List) dùng khoảng lower_bound / upper_bound của phân vùng để bỏ qua ngay cả cụm Manifest của các tháng khác; Cấp 2 (Manifest File) dùng trạng thái (ADDED / EXISTING / DELETED) và thống kê cột Min/Max/Null để chỉ đích danh tệp 0003_8888.parquet mà không cần gửi hàng nghìn lệnh HTTP mở Footer trên S3!

Apache Hudi: Trục thời gian Timeline, File Groups & Hệ thống Indexing

Hudi (Hadoop Update Delete Incremental) được thiết kế chuyên biệt cho các luồng Streaming Upsert / CDC tốc độ cao với trục thời gian trạng thái giao dịch (Timeline) và hệ thống chỉ mục định vị bản ghi (Indexing Subsystem):

Ba trụ cột kiến trúc của Apache Hudi: (1) Hudi Timeline quản lý trạng thái giao dịch qua 3 bước REQUESTED → INFLIGHT → COMPLETED; (2) Hệ thống chỉ mục Indexing (.hoodie/metadata) ánh xạ khóa bản ghi #8888 về đúng FileGroup ID; (3) File Groups & File Slices kết hợp Base File (Parquet cột) và Log Files (Avro dòng).
  • Máy trạng thái 3 bước của Hudi Timeline, Hybrid File Groups & 4 Loại Chỉ mục (Apache Hudi: The Definitive Guide, tr. 34–58):
    • Hudi Timeline & File Groups: Mọi hành động (commit cho COW, deltacommit cho MOR, compaction, clustering, clean) trong thư mục .hoodie/ đều đi qua 3 trạng thái nguyên tử: REQUESTED → INFLIGHT → COMPLETED (người đọc chỉ thấy các Instant đã COMPLETED). Mỗi File Group kết hợp tuần tự hóa lai (Hybrid Serialization): Base File dạng cột (Parquet/ORC) lưu dữ liệu chính + Log Files dạng dòng (.log.avro) bắt tức thì các bản ghi CDC mới.
    • 4 loại Index trong bảng Metadata nội bộ (.hoodie/metadata dạng HFile): Giúp định vị ngay Đơn #8888 nằm ở File Group nào mà không cần quét bảng: (1) Bloom Index (mặc định: dùng Bloom Filter + Min/Max), (2) Simple Index (đối chiếu khi cập nhật rải rác), (3) Bucket Index (băm trực tiếp hash(record_key) % N vào Bucket không cần tra cứu), và (4) Record-Level Index (RLI) (ánh xạ 1-1 từng khóa RecordKey → FileGroupId với tốc độ O(1) cho bảng hàng trăm tỷ dòng).

Hợp nhất Đa Định dạng: Delta UniForm, Apache XTable & Pluggable Table Format

Vì cả 3 định dạng bảng đều lưu dữ liệu gốc trên tệp Parquet và chỉ khác nhau ở lớp Metadata, các công cụ hiện đại có thể đọc chéo nhau thông qua kiến trúc chuyển đổi siêu dữ liệu đa chiều:

Kiến trúc dịch siêu dữ liệu đa chiều (UniForm / Apache XTable): cho phép Spark, Trino, Snowflake và Flink cùng đọc chung 1 bộ tệp vật lý orders_8888.parquet thông qua lớp Metadata tương ứng mà không cần nhân bản dữ liệu trên S3.
  • Delta Lake UniForm (Universal Format): Chỉ cần bật thuộc tính 'delta.universalFormat.enabledFormats' = 'iceberg' (và yêu cầu bật delta.columnMapping.mode = 'name' hoặc 'id'), sau mỗi giao dịch Delta thành công, hệ thống tự động sinh bất đồng bộ siêu dữ liệu chuẩn Iceberg hoặc Hudi cho cùng bộ tệp Parquet đó.
  • Hudi Pluggable Table Format & Apache XTable (tiền thân là OneTable): Hudi tách rời động cơ lưu trữ khỏi định dạng bảng, kết hợp với Apache XTable để dịch siêu dữ liệu qua lại đa chiều (omnidirectional interoperation) giữa cả 3 định dạng Hudi, Iceberg và Delta Lake, giúp tích hợp dễ dàng với mọi danh mục như Snowflake Polaris hay DataHub mà vẫn giữ nguyên bảng gốc.
Tiêu chí kỹ thuật Delta Lake Apache Iceberg Apache Hudi
Cơ chế Metadata cốt lõi Nhật ký giao dịch tuần tự _delta_log (000000.json + .checkpoint.parquet + _last_checkpoint). Cây siêu dữ liệu 3 tầng: Catalog (CAS) → Metadata file (.json) → Manifest List (.avro) → Manifest file (.avro). Timeline (commit / deltacommit qua 3 bước trạng thái) + File Groups (Base Parquet + Log Avro).
Vũ khí đặc trưng nhất Tích hợp hoàn hảo với Apache Spark Structured Streaming, tối ưu hóa Z-Order / Liquid Clustering, Deletion Vectors, Change Data Feed (CDF) & UniForm. Hidden Partitioning và Partition Evolution (đổi phân vùng không cần viết lại bảng), cắt tỉa 2 cấp ở quy mô Petabyte, chuẩn mở đa động cơ (Trino, Snowflake, Spark, Flink). Hệ thống Indexing tích hợp sẵn (Record-Level Index, Bucket Index) & kiểm soát đồng thời NBCC, cực mạnh cho Streaming Upsert / CDC tần suất cao.
Cơ chế Xóa / Cập nhật dòng (MOR) Mặc định COW; chuyển sang MOR bằng Deletion Vectors (mảng Roaring Bitmap lưu vị trí dòng xóa). Hỗ trợ cả COW lẫn MOR qua Positional Delete Files (vị trí dòng) và Equality Delete Files (điều kiện khóa). Thiết kế gốc phân tách 2 loại bảng COPY_ON_WRITE và MERGE_ON_READ (Base Parquet + Delta Log Avro).
Tương thích chéo Sinh metadata Iceberg/Hudi qua Delta UniForm. Đọc/dịch qua lại nhờ Apache XTable hoặc Snapshot migration. Kiến trúc Pluggable Table Format & tích hợp Apache XTable.

Trạm 6.3: Bộ tính năng cốt lõi — ACID, concurrency (Occ/mvcc/nbcc), Time Travel & schema

Giao dịch ACID & Ba Cơ chế Kiểm soát Đồng thời (Concurrency Control)

Khi nhiều luồng CDC, ETL Compaction và truy vấn BI đọc/ghi đồng thời trên Đơn hàng #8888, lớp Transaction Layer đảm bảo tính ACID (Atomicity, Consistency, Isolation, Durability) thông qua 3 cơ chế kiểm soát đồng thời:

Sự kết hợp giữa MVCC (Cô lập Snapshot giúp Đọc và Ghi không bao giờ khóa nhau), OCC (Kiểm soát lạc quan phát hiện xung đột cấp độ tệp giữa các luồng Ghi) và NBCC (Kiểm soát đồng thời không khóa cho nhiều luồng Streaming trên Apache Hudi).
  • Phát hiện Xung đột Cấp Tệp (File-Level Conflict Detection) & Mức Cô lập: Trong OCC, Writer 2 chỉ bị từ chối (ConcurrentModificationException) khi sửa/xóa đúng tệp Parquet vật lý mà Writer 1 vừa chạm tới; nếu 2 luồng cùng APPEND hoặc UPDATE trên 2 Partition tách biệt, cả hai đều commit thành công lên v3. Mặc định Delta Lake dùng mức cô lập WriteSerializable (thay vì Serializable cứng nhắc) để cho phép các thao tác blind append chạy song song không chặn lệnh bảo trì OPTIMIZE / Z-ORDER.

Du hành thời gian (Time Travel), Change Data Feed (CDF) & Tiến hóa Lược đồ (Schema Evolution)

Vì tệp Parquet là bất biến và mỗi giao dịch tạo một Version / Snapshot mới, đồng thời mỗi cột được định danh bằng mã số nguyên bất biến (Column ID / Field ID), Lakehouse giải quyết trọn vẹn cả bài toán truy vấn lịch sử lẫn đổi tên cột trong 1 ms:

Cơ chế Time Travel qua chuỗi Snapshot v0 -> v1 -> v2 kèm luồng thay đổi tăng trưởng Change Data Feed (CDF) và bí mật định danh cột bằng mã số nguyên bất biến (Column ID / Field ID) giúp đổi tên cột chỉ bằng 1 thao tác sửa JSON Metadata mà không viết lại tệp Parquet. 
-- [A] DELTA LAKE (Truy vấn theo Timestamp, Version & Khôi phục bảng):
SELECT * FROM sales.orders TIMESTAMP AS OF '2026-10-15 14:00:00' WHERE order_id = 8888;
SELECT * FROM sales.orders VERSION AS OF 0 WHERE order_id = 8888;
RESTORE TABLE sales.orders TO VERSION AS OF 0;

-- [B] APACHE ICEBERG (Chuẩn SQL:2011 System-Versioned Tables):
SELECT * FROM sales.orders FOR SYSTEM_TIME AS OF TIMESTAMP '2026-10-15 14:00:00' WHERE order_id = 8888;
SELECT * FROM sales.orders FOR SYSTEM_VERSION AS OF 5789718362515484664 WHERE order_id = 8888;
CALL catalog.system.rollback_to_snapshot('sales.orders', 5789718362515484664);

-- [C] ĐỌC LUỒNG THAY ĐỔI TĂNG TRƯỞNG (CHANGE DATA FEED - CDF TRÊN DELTA LAKE):
SELECT order_id, so_tien, _change_type, _commit_version, _commit_timestamp
FROM table_changes('sales.orders', 0, 1) WHERE order_id = 8888;
  • Time Travel & Change Data Feed (CDF): Phục vụ kiểm toán pháp lý, tái lập tập dữ liệu huấn luyện ML, và Rollback tức thời. Khi bật delta.enableChangeDataFeed = true (hoặc Incremental Query trên Hudi / Changelog Scan trên Iceberg), bảng tự động xuất các dòng biến động kèm _change_type (insert, update_preimage = 15M, update_postimage = 14M, delete) để pipeline Silver → Gold chỉ đọc phần chênh lệch.
  • Schema Enforcement & Schema Evolution bằng Column ID: Chặn đứng dữ liệu sai kiểu ngay lúc ghi (như cố chèn chuỗi 'Mười lăm triệu' vào cột DECIMAL). Khi đổi tên cột (RENAME COLUMN total_cost TO order_amount), nhờ Iceberg (mặc định) và Delta Lake (Column Mapping Mode = 'id') ánh xạ cột theo field-id bất biến thay vì tên chữ như Hive cũ, hệ thống chỉ đổi nhãn hiển thị của ID 2 trong JSON Metadata mà không bao giờ gặp lỗi trả về NULL hay làm "sống dậy" cột cũ đã xóa.
  • Unified Batch & Streaming: Một bảng Lakehouse duy nhất vừa làm nguồn/đích cho luồng thời gian thực (Spark Structured Streaming) vừa phục vụ truy vấn lô (Batch BI) trên cùng một bộ API.

Trạm 6.4: Chiến lược ghi & cập nhật — Copy-on-Write (COW) vs. Merge-on-Read (MOR)

Khi tệp file_01.parquet nặng 100 MB chứa 100.000 đơn hàng và khách hàng nhập mã giảm giá làm số tiền Đơn hàng #8888 đổi từ 15.000.000đ thành 14.000.000đ, vì tệp Parquet trên S3 là bất biến (Immutable), động cơ Lakehouse có đúng 2 chiến lược để thực thi lệnh UPDATE:

Đối chiếu hai chiến lược cập nhật trên Lakehouse: (1) Copy-on-Write (COW) viết lại toàn bộ tệp Parquet 100 MB để tối ưu tốc độ đọc tuyệt đối; (2) Merge-on-Read (MOR) chỉ ghi 1 dòng thay đổi (~1 KB) vào tệp Log/Delete rồi trộn khi đọc để tối ưu tốc độ ghi Streaming/CDC.
Tiêu chí so sánh Copy-on-Write (COW) Merge-on-Read (MOR)
Cơ chế khi UPDATE / DELETE Viết lại toàn bộ tệp cột (Parquet) mới chứa bản ghi đã sửa và đổi con trỏ Metadata (commit). Giữ nguyên tệp gốc (Base Parquet), chỉ ghi nối đuôi bản ghi thay đổi vào Log file (Avro) hoặc Delete file (deltacommit).
Chi phí GHI (Write Amplification) Cao (WAF >> 1): Sửa 1 dòng 1 KB phải viết lại cả tệp 100 MB (khuếch đại gấp 100.000 lần). Cực thấp (WAF ≈ 1): Ghi nối đuôi tức thì chỉ tốn vài Kilobyte.
Tốc độ ĐỌC (Query Latency) Nhanh tuyệt đối cho OLAP/BI: Quét thẳng tệp Parquet mới nhất, không tốn CPU ghép trộn. Tốn chi phí trộn khi đọc: Phải hợp nhất Base file + Log / Delete file lúc truy vấn (định kỳ gom lại nhờ Compaction).
Góc nhìn Đọc & Cơ chế Xóa (Sách gốc) Đọc trực tiếp Snapshot Parquet thuần túy. • Hudi 2 chế độ đọc: Snapshot Query (RT) trộn Base+Log lấy dữ liệu tươi từng giây vs. Read-Optimized (RO) chỉ đọc Base Parquet.

• Iceberg 2 loại Delete Files: Positional Delete lưu (file_path, pos = 4512) đọc cực nhanh vs. Equality Delete lưu (order_id = 8888) ghi nhanh tuyệt đối (Zero-read at write time).
Trường hợp sử dụng lý tưởng Tác vụ nạp theo lô (Batch ETL), bảng tầng Gold phục vụ Dashboard BI. Luồng Streaming / CDC (Debezium + Kafka) Upsert / Delete liên tục tại tầng Bronze / Silver.

Trạm 6.5: Năm kỹ thuật tối ưu vật lý sống còn trên Lakehouse

Hidden Partitioning & Partition Evolution (Apache Iceberg)

Khắc phục điểm mù của Hive Partitioning truyền thống (bắt người dùng phải nhớ lọc đúng cột thư mục phái sinh nam_thang và không thể đổi cách chia phân vùng nếu không viết lại toàn bộ bảng), Iceberg lưu trực tiếp 6 hàm biến đổi chuẩn (year, month, day, hour, bucket[N], truncate[L]) vào trong Partition Spec của Metadata:

Cơ chế Hidden Partitioning và Partition Evolution của Apache Iceberg: lưu hàm biến đổi phân vùng ngay trong Partition Spec của Metadata giúp tự động cắt tỉa phân vùng từ cột thời gian gốc và tiến hóa chiến lược phân vùng mà không cần viết lại dữ liệu cũ.

Gom cụm Đa chiều: Từ Z-Ordering sang Liquid Clustering (Hilbert Curve)

Khi một phân vùng có hàng nghìn tệp Parquet và dữ liệu khách hàng Bình Dương mua Sofa bị rải đều khắp các tệp, khoảng [Min, Max] của tệp nào cũng trải rộng từ A → Z làm tê liệt Data Skipping. Kỹ thuật Z-Ordering (đan xen bit nhị phân theo đường cong chữ Z) và thế hệ mới Liquid Clustering (CLUSTER BY theo đường cong Hilbert Curve) gom các dòng cùng khóa đa chiều về chung tệp vật lý:

So sánh hiệu quả Data Skipping trước và sau khi chạy Z-Ordering / Liquid Clustering: thu hẹp khoảng giá trị [min, max] trên từng tệp Parquet giúp động cơ truy vấn tìm Đơn hàng #8888 chỉ bằng cách đọc File 1 và bỏ qua ngay File 2.
  • Tại sao Liquid Clustering (Hilbert Curve) vượt trội hơn Z-Ordering (Delta Lake: The Definitive Guide, tr. 127–131, 259–263): Z-Order suy giảm hiệu quả khi vượt quá 3–4 cột và không có tính tăng trưởng (not incremental) — mỗi lần có dữ liệu mới lại phải viết lại cả phân vùng. Ngược lại, Liquid Clustering gom cụm tăng trưởng chỉ trên các tệp mới nạp, bảo toàn tính lân cận không gian tốt hơn nhờ đường cong Hilbert, và cho phép đổi khóa gom cụm (ALTER TABLE ... CLUSTER BY) tức thời không cần viết lại bảng.

Bộ 3 Dịch vụ Bảo trì Vật lý: Compaction (OPTIMIZE), Deletion Vectors & Vacuum

Để trị dứt điểm căn bệnh 43.200 tệp nhỏ li ti (Small File Problem) từ luồng Streaming, tăng tốc xóa/sửa dòng trên bảng COW, và thu hồi dung lượng S3 an toàn (cũng như xóa vĩnh viễn dữ liệu cá nhân theo luật GDPR qua quy trình 3 bước: DELETE → REORG PURGE / OPTIMIZE → VACUUM), kỹ sư dữ liệu vận hành phối hợp 3 dịch vụ dưới đây:

Sự phối hợp giữa 3 dịch vụ bảo trì vật lý: (1) Compaction (OPTIMIZE) gộp hàng vạn tệp nhỏ thành tệp chuẩn 128 MB – 1 GB; (2) Deletion Vectors dùng Roaring Bitmap đánh dấu xóa mềm tức thì; (3) Vacuum / Expire Snapshots dọn rác vật lý sau chu kỳ lưu giữ 168 giờ.

Tóm tắt bỏ túi Chặng 6 (Lakehouse & Open Table Formats)

  1. Kiến trúc Lakehouse (CIDR 2021): Hợp nhất chi phí rẻ và tính mở của Data Lake (Object Storage + Parquet) với tính toàn vẹn ACID, Schema Enforcement và hiệu năng BI (nhờ Hot Caching, Auxiliary Data & Vectorized Execution) của Data Warehouse, đồng thời tách rời hoàn toàn Compute và Storage.
  2. Định nghĩa lại Một Bảng bằng Bộ ba Open Table Formats: Thay vì định nghĩa bảng bằng thư mục như Hive cũ, bộ ba Open Table Formats định nghĩa bảng bằng danh sách tệp hợp lệ trong Metadata: Delta Lake dùng nhật ký tuần tự _delta_log (6 loại Action + Checkpoint Parquet + _last_checkpoint), Apache Iceberg dùng cây 3 tầng (Catalog CAS → Metadata → Manifest List → Manifest File kèm Hidden Partitioning & Partition Evolution), và Apache Hudi dùng Timeline (3 trạng thái) + File Groups + Indexing (RLI/Bloom/Bucket) — và chúng có thể đọc chéo nhau trên cùng 1 bộ tệp Parquet nhờ Delta UniForm / Apache XTable.
  3. Bộ Tính năng Cốt lõi & Chiến lược Ghi/Đọc: Bảng Lakehouse cung cấp ACID & Concurrency (MVCC, OCC phát hiện xung đột cấp tệp, NBCC), Time Travel (Snapshots / Rollback / Change Data Feed), Schema Evolution (nhờ Column ID bất biến), và cho phép chọn giữa Copy-on-Write (COW - tối ưu Đọc) hoặc Merge-on-Read (MOR - tối ưu Ghi/Streaming với Positional / Equality Deletes).
  4. Năm kỹ thuật bảo trì vật lý: Giúp bảng luôn chạy ở tốc độ đỉnh cao: Compaction (Small File Problem), Hidden Partitioning & Partition Evolution, Z-Ordering / Liquid Clustering (Hilbert Curve), Deletion Vectors (Roaring Bitmap), và Vacuum / Snapshot Expiration (168 giờ & tuân thủ GDPR).
