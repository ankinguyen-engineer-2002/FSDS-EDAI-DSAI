Trước khi đi sâu vào cấu trúc Hypervisor và Container Engine, hãy phân biệt rạch ròi giữa công nghệ ảo hóa nền tảng (VM / Container) với các gói dịch vụ hạ tầng thương mại (Shared Hosting, VPS, Cloud VM, Dedicated Server, Container, Serverless). Tương tác trực tiếp với 8 Slide Mô phỏng 2D dưới đây để quan sát sự tiến hóa hạ tầng qua bài toán thực tế:

So sánh trực diện 3 thế hệ hạ tầng: (1) Bare Metal lãng phí 90–95% CPU & Shared Hosting dính hiệu ứng Noisy Neighbor (503); (2) VM / VPS / Cloud VM cắt máy bằng Hypervisor nhưng chịu thuế VM Tax (mỗi VM gánh 1 Guest OS hàng GB); (3) Container dùng chung Host OS Kernel, nhẹ vài MB, khởi động 1 giây, mật độ 50+ Containers/host.

Trạm 1.1: Bare Metal (Lãng phí 90–95% CPU) & Virtual Machines (Hypervisor Type 1 & Type 2, Guest OS, VM Tax)

Khi dịch vụ order-api (app.py) chạy đơn độc trên một máy chủ vật lý (Bare Metal Server), nó chỉ tiêu thụ vỏn vẹn 5–10% năng lực CPU và RAM, bỏ hoang 90–95% phần cứng đắt đỏ. Thế nhưng kỹ sư không thể cài trực tiếp nhiều ứng dụng lên chung một hệ điều hành vì rủi ro xung đột thư viện (Dependency Hell — ví dụ order-api cần Python 3.11 + libpq v15 trong khi dịch vụ kế toán cũ cần Python 2.7 + libpq v10) và nguy cơ một ứng dụng lỗi kéo sập toàn máy chủ. Công nghệ ảo hóa phần cứng (Hardware Virtualization) sử dụng Hypervisor để cắt tài nguyên vật lý thành nhiều Virtual Machines (VMs) đã giải quyết triệt để bài toán cô lập, nhưng đồng thời áp lên hệ thống một khoản chi phí nặng nề: "Thuế máy ảo" (VM Tax) — mỗi VM phải tự cõng một bản Guest OS riêng biệt nặng hàng chục GB, khởi động mất nhiều phút và giới hạn mật độ ở ngưỡng ~10 VMs/host.

Về mặt kiến trúc (Docker Deep Dive & Slide bài giảng), Hypervisor chia thành hai nhánh với đường đi lệnh khác biệt rõ rệt:

  • Hypervisor Type 1 (Bare-metal Hypervisor) (VMware ESXi, Microsoft Hyper-V, Xen, hoặc Linux KVM tích hợp ngay trong nhân Linux): Đường đi của lệnh là [App: order-api] → [Guest OS Kernel] → [Hypervisor] → [CPU / Memory Vật lý]. Đây là chuẩn bắt buộc trong các Data Center của VPS và Cloud VM nhờ giao tiếp sát phần cứng với độ trễ thấp.
  • Hypervisor Type 2 (Hosted Hypervisor) (QEMU, Oracle VirtualBox, Parallels, VMware Fusion/Workstation): Đường đi của lệnh là [App: order-api] → [Guest OS Kernel] → [Hypervisor Program] → [Host OS] → [CPU / Memory Vật lý]. Mô hình này chịu độ trễ cao hơn vì mỗi lệnh chạm phần cứng phải đi vòng qua cả Guest OS lẫn Host OS, chỉ phù hợp làm môi trường thử nghiệm trên máy trạm cá nhân.
Đối chiếu kiến trúc Bare Metal đơn lẻ (chỉ dùng 5–10% CPU, lãng phí 90–95% vì sợ Dependency Hell) với kiến trúc Virtual Machines trên Hypervisor Type 1 / Type 2 (mỗi VM phải cõng thêm một Guest OS nặng hàng chục GB, boot mất nhiều phút, tối đa ~10 VMs/host).

Đơn vị ảo hóa Không ảo hóa (Cài trực tiếp lên sắt). Phần cứng vật lý (Hardware-level Virtualization). Hypervisor giả lập cả CPU, RAM, Card mạng, Ổ đĩa ảo cho từng VM.
Hiệu suất sử dụng phần cứng Cực thấp: Chỉ khai thác 5–10% CPU & RAM. Cao hơn Bare Metal nhưng bị đánh thuế VM Tax. Mỗi VM phải cõng thêm 1 Guest OS hoàn chỉnh.
Dung lượng hao phí (Size) Toàn bộ ổ đĩa vật lý của máy chủ. Nặng hàng chục GB (hundreds/thousands of MBs) cho mỗi OS. Chạy 100 bản sao order-api bằng VM đồng nghĩa phải nuôi 100 bản Guest OS.
Độ trễ khởi động (Boot time) Mất nhiều phút (bật nguồn vật lý). Chậm: Tính bằng phút để nạp từng Guest Kernel. Không thể mở rộng tức thì khi lưu lượng đơn hàng tăng đột biến.
Mật độ đóng gói trên 1 Host 1 ứng dụng duy nhất / máy chủ. Sức chứa tối đa khoảng ~10 VMs / máy chủ. Tốn chi phí bản quyền OS, công sức vá lỗi (patching) và giám sát (monitoring).

Hypervisor mang lại biên giới an toàn tuyệt đối ở cấp độ phần cứng: nếu VM 1 bị Kernel Panic, VM 2 và VM 3 vẫn hoạt động bình thường vì sở hữu Guest OS tách biệt. Tuy nhiên, để chạy một tệp app.py chỉ nặng vài chục KB mà phải cấp phát cả một hệ điều hành nặng hàng GB RAM/Disk và chờ khởi động hàng phút là sự lãng phí quá lớn. Làm thế nào để giữ được sự cô lập môi trường cho từng ứng dụng nhưng loại bỏ hoàn toàn tầng Guest OS trùng lặp? Đó là bước nhảy vọt sang mô hình Container ở Trạm 1.2.

Trạm 1.2: Container Model (OS-level Virtualization, Shared Host OS Kernel, 50+ Containers/host)

Container (OS-level Virtualization — Ảo hóa cấp độ hệ điều hành) cắt bỏ hoàn toàn tầng Hypervisor và các bản Guest OS trùng lặp: mọi Container trên cùng một máy chủ đều dùng chung nhân hệ điều hành đã khởi động sẵn (Shared Host OS Kernel) và chỉ đóng gói mã nguồn ứng dụng cùng các thư viện nhị phân tối thiểu (Bins/Libs). Nhờ kiến trúc này, kích thước gói của order-api giảm từ hàng chục GB xuống chỉ còn vài MB, thời gian khởi động rút ngắn từ hàng phút xuống tính bằng giây, và mật độ triển khai tăng vọt lên 50+ Containers/host (gấp 3x–5x so với VM).

Một hệ quả cơ học quan trọng cần lưu ý khi làm việc đa nền tảng (Docker Deep Dive): vì tiến trình bên trong Linux Container gọi trực tiếp Linux System Calls xuống nhân hệ điều hành bên dưới nên nó bắt buộc phải chạy trên một Linux Kernel. Do đó, trên máy tính Windows, các container Linux chạy thông qua nhân Linux thật của WSL 2 (Windows Subsystem for Linux 2); còn trên máy Mac (vốn chạy nhân XNU / Darwin của macOS), các công cụ như Docker Desktop, OrbStack hay Podman Machine sẽ tự động khởi chạy một máy ảo Linux siêu nhẹ (Lightweight Linux VM) ở tầng ngầm để cung cấp Shared Linux Kernel cho toàn bộ containers bên trên.

Phẫu thuật sự khác biệt giữa Virtual Machine (cõng 3 bản Guest OS nặng hàng GB trên Hypervisor, tối đa ~10 VMs/Server) và Container (chỉ đóng gói App + Bins/Libs vài MB trên Container Engine và dùng chung Shared Linux Kernel đã boot sẵn, đạt mật độ 50+ Containers/Server).
Thông số kỹ thuật (Feature) Virtual Machines (Máy ảo) Containers (Đóng gói cấp độ OS) Chênh lệch định lượng (Từ Sách & Slide)
Hệ điều hành (OS) Full Guest OS riêng cho từng máy ảo. Share Host Kernel (Dùng chung nhân HĐH chủ). Cắt giảm từ 100 OS xuống còn 0 OS phụ trội khi chạy 100 apps.
Thời gian khởi động (Startup) Chậm (Slow — tốn thời gian boot OS). Tức thì (Fast — Host OS đã chạy sẵn). Từ nhiều phút giảm xuống chỉ còn vài giây (hoặc mili-giây).
Kích thước gói (Size) Hàng Gigabytes (GBs). Vài Megabytes (MBs). Chỉ chứa code app.py và các thư viện tối thiểu (Bins/Libs).
Mật độ trên 1 Server Khoảng ~10 VMs. Vượt trội: 50+ Containers. Hiệu suất mật độ tăng gấp 3x đến 5x trên cùng một phần cứng.
Cấp độ cô lập (Isolation) Cấp độ phần cứng (Hardware-level). Cấp độ tiến trình (Process-level). Bề mặt tấn công (Attack surface) nhỏ hơn nhưng dùng chung Kernel.
