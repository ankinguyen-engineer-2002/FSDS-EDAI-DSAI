Ở Chặng 2, chúng ta đã mổ xẻ các bánh răng tầng nhân Linux (Namespaces, cgroups v2, OverlayFS, Seccomp). Bước vào Chặng 3 (Trạm 3.1 → 3.2): Chu trình Build-Ship-Run & Động cơ OCI Runtime, chúng ta khám phá cách Docker và chuẩn mở OCI (Open Container Initiative) gói gọn hàng chục thao tác Kernel phức tạp thành dây chuyền công nghiệp Build - Ship - Run, giải cứu dữ liệu PostgreSQL khỏi lớp UpperDir tạm bợ bằng Docker Volumes, và phẫu thuật chuỗi tiến trình bên dưới lệnh docker run đối chiếu với nhánh Daemonless / Rootless của Podman.

Sơ đồ 3.0: Kiến trúc Tổng quan Chặng 3 — Chu trình Build-Ship-Run, Persistent Volumes & Chuỗi Động cơ OCI Runtime

Giải phẫu 2 nửa của hệ sinh thái Container: (1) Chu trình Build - Ship - Run đóng gói order-api qua Dockerfile (Multi-stage Build) và tách dữ liệu PostgreSQL khỏi lớp UpperDir tạm bợ sang Persistent Volume; (2) Chuỗi lắp ráp Docker CLI → dockerd → containerd → containerd-shim → runc (trong đó runc dựng xong container thì lập tức tự thoát để tạo Daemonless containers).

Trạm 3.1: Workflow Vĩ mô Build - Ship - Run (Dockerfile, Multi-stage Build, OCI Image, Registry & Persistent Volumes)

  • [Bối cảnh & Ẩn dụ đời thực — Dây chuyền sản xuất thực phẩm đóng hộp công nghiệp]: Hãy hình dung việc triển khai order-api giống như dây chuyền sản xuất thực phẩm đóng hộp công nghiệp:
    1. Build (Đóng gói): Bạn viết công thức nấu ăn (Dockerfile), đưa vào dây chuyền (docker build) để đóng thành các hộp đồ hộp hút chân không dán nhãn niêm phong bất biến (OCI Image — đóng vai trò như một khuôn mẫu Class trong lập trình hướng đối tượng).
    2. Ship (Phân phối): Bạn chở các thùng đồ hộp này lên kho trung chuyển toàn cầu (OCI Registry như Docker Hub hoặc Harbor) qua lệnh docker push / docker pull.
    3. Run (Thực thi): Tại bất kỳ máy chủ nào, bạn chỉ cần khui hộp (docker run) để biến gói tĩnh thành một bữa ăn đang bốc khói (Container — thực thể đang sống Object instance của Image).
  • [Nỗi đau (Pain Point) từ trạm trước — Hiểm họa Mất sạch Database trong Lớp UpperDir Tạm bợ]: Ở Trạm 2.3, chúng ta biết mỗi Container được cấp một lớp ghi mỏng UpperDir (Thin Writable Layer) để lưu các thay đổi phát sinh trong lúc chạy. Nhưng nỗi đau chí mạng nằm ở chỗ: Lớp UpperDir này có tính chất tạm bợ (Ephemeral), gắn chặt với vòng đời của Container. Khi bạn nâng cấp phiên bản mới cho Database PostgreSQL (xóa container cũ, bật container mới theo triết lý bất biến Immutable), toàn bộ dữ liệu đơn hàng nằm trong UpperDir sẽ bốc hơi vĩnh viễn! Do đó, hệ sinh thái Container cung cấp 3 cơ chế lưu trữ phân biệt rõ rệt: (1) Writable Layer (UpperDir) tạm bợ dùng cho file nháp; (2) Bind Mounts ánh xạ trực tiếp thư mục của Host vào Container; và (3) Docker Volumes tại /var/lib/docker/volumes hoàn toàn độc lập với vòng đời Container — chuẩn mực bắt buộc khi vận hành Database Stateful!
# Cấu trúc dự án: project/app.py & project/Dockerfile (Chuẩn hóa từ Slide bài giảng)
# Use official Python image
FROM python:3.11-slim

# Set working directory
WORKDIR /app

# Copy files into container
COPY app.py .

# Run the app (PID 1 bên trong Container)
CMD ["python", "app.py"]

Sơ đồ 3.1: Tầng 1 Workflow Vĩ mô — Chu trình Build - Ship - Run & Cơ chế Lưu trữ Bền vững (Docker Volume)

Luồng Build - Ship - Run từ Dockerfile (FROM python:3.11-slim) thành OCI Image bất biến đẩy lên Registry, kết hợp gắn kết 2 chiều Docker Volume (/var/lib/docker/volumes) tách rời khỏi vòng đời Container để bảo vệ dữ liệu PostgreSQL.
Giai đoạn / Khái niệm Bản chất Cơ học (Slide & Excalidraw Notes) Hành vi đối với order-api (Stateless) & PostgreSQL (Stateful)
Dockerfile Văn bản chứa toàn bộ công thức lắp ráp môi trường (chỉ thị FROM, WORKDIR, COPY, CMD và kỹ thuật Multi-stage Build tạo ảnh siêu gọn). Chuẩn hóa 100% môi trường chạy app.py trên nền python:3.11-slim, xóa sổ căn bệnh "chạy được trên máy tôi nhưng lỗi trên server".
OCI Image Gói phần mềm tĩnh, bất biến (Immutable, Read-Only Layers kèm OCI Manifest JSON mô tả cấu hình, mã băm SHA-256 Digest và kiến trúc CPU ARM/AMD). Một Image order-api duy nhất có thể dùng làm khuôn đúc ra hàng chục Containers chạy song song.
Docker Container Thuật ngữ thể hiện "sự sống của Image": là 1 tiến trình đang chạy (Running process) cộng với 1 lớp ghi mỏng Thin Writable Layer. Container chỉ sống chừng nào tiến trình chính (PID 1: python app.py) còn sống; nếu tiến trình này kết thúc (killed), container lập tức dừng lại.
Docker Volume vs. Writable Layer Writable Layer bị xóa sổ cùng container; Volume là đối tượng độc lập lưu tại /var/lib/docker/volumes nằm ngoài vòng đời container. order-api (phi trạng thái — Stateless) chỉ cần Writable Layer cho file nháp; riêng PostgreSQL (có trạng thái — Stateful) bắt buộc phải gắn Volume để khi xóa/nâng cấp container Database không bị mất dữ liệu.

[Đúc kết Cơ học & Đánh đổi (Trade-off)]: Chu trình Build → Ship → Run kết hợp với Docker Volume đã giúp kỹ sư đóng gói và vận hành cả ứng dụng Stateless (order-api) lẫn Stateful (PostgreSQL) một cách trơn tru. Thế nhưng, khi bạn gõ lệnh docker run trên màn hình Terminal, một chuỗi phản ứng dây chuyền nào thực sự nổ ra bên dưới nắp capo để nối từ câu lệnh chữ cái đến các lời gọi clone(2) của Linux Kernel? Hơn nữa, tại sao kiến trúc chạy ngầm của Docker lại bị coi là có lỗ hổng bảo mật lớn trên máy chủ dùng chung, dẫn đến sự ra đời của Podman? Chúng ta bước sang Trạm 3.2.

Trạm 3.2: Giải phẫu Động cơ OCI Runtime (dockerd → containerd → shim → runc) & Hệ sinh thái Công cụ

  • [Bối cảnh & Ẩn dụ đời thực — Dây chuyền lắp ráp xe hơi chuyên môn hóa]: Thời kỳ đầu, Docker Engine là một khối sắt nguyên khối (Monolithic binary) ôm đồm mọi việc và phụ thuộc vào thư viện LXC cũ kỹ. Sau cuộc đại phẫu theo chuẩn mở OCI (Open Container Initiative), Docker Engine được tách thành một dây chuyền lắp ráp xe hơi chuyên môn hóa:
    • dockerd (Docker Daemon — /usr/bin/dockerd): Là "Quầy lễ tân kiêm Tổng đài API" nhận phiếu yêu cầu REST qua /var/run/docker.sock từ khách hàng.
    • containerd (High-level Runtime — /usr/bin/containerd): Là "Quản đốc phân xưởng" quản lý vòng đời từ tải ảnh, giải nén OCI Bundle đến ra lệnh bật/tắt qua gRPC.
    • containerd-shim (/usr/bin/containerd-shim-runc-v2): Là "Người bảo mẫu" đứng canh ngay cạnh từng chiếc nôi container, giữ mở STDIN/STDOUT và báo cáo Exit Code.
    • runc (Low-level Runtime — /usr/bin/runc): Là "Anh thợ xây cơ bắp" bọc thư viện libcontainer trực tiếp cầm bản vẽ OCI Bundle xuống nói chuyện với Linux Kernel để dựng tường Namespaces và lắp cầu dao cgroups; dựng xong nhà cho tiến trình ở là anh thợ xây lập tức rút lui (exit) trả lại mặt bằng!
  • [Nỗi đau (Pain Point) từ trạm trước — Điểm lỗi đơn SPOF và Rủi ro Quyền Root của dockerd]: Nếu giữ nguyên kiến trúc nguyên khối cũ (mọi container đều là tiến trình con trực tiếp của Docker Daemon), chỉ cần kỹ sư nâng cấp hoặc khởi động lại dockerd, toàn bộ hàng chục containers đang phục vụ khách hàng trên máy chủ đó sẽ bị giết chết theo (Single Point of Failure)! Chưa kể, bản thân dockerd luôn phải chạy ngầm 24/7 với quyền quản trị tối cao (Root / Admin access) — nếu kẻ tấn công đục thủng được dockerd, chúng sẽ chiếm trọn quyền điều khiển máy chủ. Đó là lý do Red Hat phát triển bộ ba Podman + Buildah + Skopeo hoạt động hoàn toàn không cần Daemon (Daemonless) và không cần quyền Root (Rootless)!

Sơ đồ 3.2: Tầng 2 OCI Runtime Engine — Chuỗi Tiến trình Điều phối (Docker Daemon) & Nhánh rẽ Daemonless (Podman)

Đối chiếu 2 nhánh thực thi chuẩn OCI: Nhánh 1 (Docker CLI → dockerd → containerd → containerd-shim) và Nhánh 2 (Podman CLI / Buildah / Skopeo bỏ qua Daemon chạy Rootless) cùng hội tụ tại runc (libcontainer) để cấu hình Linux Kernel rồi runc lập tức tự thoát.
Phân nhóm Hạ tầng (Slide) Công cụ đại diện Trách nhiệm cốt lõi & Cơ chế vận hành (Từ Slide & Sách) Đánh đổi Kỹ thuật (Trade-offs)
01. Container Tools
(Công cụ cấp người dùng)		 Docker vs. Podman. Docker dùng kiến trúc Client-Daemon qua /var/run/docker.sock. Podman (dùng thư viện libpod) chạy trực tiếp container không cần Daemon (Daemonless) và không cần quyền Root (Rootless). Docker có hệ sinh thái phong phú nhưng tốn tài nguyên nuôi Daemon ngầm và rủi ro quyền Root; Podman an toàn vượt trội trên máy chủ nhiều người dùng (Multi-user).
02. Container Runtime
(Động cơ thực thi)		 containerd, CRI-O (High-level) & runc, crun (Low-level). containerd (thuộc CNCF) quản lý tải ảnh và vòng đời, hỗ trợ chuẩn CRI. runc (chuẩn OCI Runtime Spec) dùng libcontainer giao tiếp trực tiếp với OS Kernel để tạo container rồi tự thoát. Tách shim và runc khỏi dockerd giúp đạt được Daemonless containers (restart Docker Daemon không làm chết app đang chạy) và cho phép cắm các runtime khác như Wasm (Spin).
03. Image Building
(Xây dựng Image)		 BuildKit / Buildx, Buildah, Kaniko. Đóng gói mã nguồn và thư viện thành định dạng OCI Image chuẩn hóa (ví dụ lệnh buildah bud đọc Containerfile/Dockerfile và buildah commit lưu thành image). Buildah và Kaniko cho phép đóng gói Image an toàn bên trong đường ống CI/CD mà không cần cấp quyền Root cho Docker Daemon.
04. Image Management
(Quản lý & Chuyển giao)		 Skopeo. Kiểm tra metadata từ xa (skopeo inspect), sao chép và đồng bộ Image giữa các Registries mà không cần tải toàn bộ về hay chạy container. Tối ưu hóa tốc độ kiểm duyệt bảo mật và di chuyển Image giữa môi trường Internet và mạng nội bộ (Air-gapped).
